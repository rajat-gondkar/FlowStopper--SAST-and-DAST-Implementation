# Benchmark target: OWASP Benchmark for Python

A third-party, intentionally vulnerable **Flask** test suite used only as a **scan target**, to measure
how well FlowStopper generalises to code we did not write. It is **not** part of our product, is
**not vendored**, and is never part of evaluation (rule R8). Choice and reasoning: decision A-70 in
`../../docs/DECISIONS_Dev1.md`.

- Upstream: https://github.com/OWASP-Benchmark/BenchmarkPython (project page:
  https://owasp.org/www-project-benchmark/)
- Pinned: commit `f1291485808b66e20ddb6b01b10dc71b3df8c8ba` (HEAD of `main`, 2026-05-19; no release tags)
- Licence: **GNU General Public License v3.0** (`GPL-3.0-only`; file headers say "version 3", no
  "or later"). We clone it locally to scan it and never modify or redistribute it, so no permission is
  needed. Credit: `../../THIRD_PARTY.md`.
- Official solution: `expectedresults-0.1.csv` in the upstream repo root (one row per test case:
  name, category, real vulnerability true/false, CWE). The per-test request recipe is
  `data/benchmark-crawler-http.xml`.

## Run

```bash
make bench-fetch BENCH_APP=owasp-benchmark-python   # clone @ pinned SHA (verified) into src/, build, start
# same as: scripts/bench_fetch.sh up owasp-benchmark-python
# Compose project: flowstopper-bench-owasp-benchmark-python
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8110/benchmark/Index.html   # wait for 200 (/ is a 302)
.venv/bin/FlowStopper scan --source bench/owasp-benchmark-python/src --target http://127.0.0.1:8110 \
    --out out/owasp-benchmark-python_first
.venv/bin/FlowStopper eval --key bench/owasp-benchmark-python/answer_key.json \
    --issues out/owasp-benchmark-python_first/issues.json --out docs/metrics/<file>.json
make bench-down BENCH_APP=owasp-benchmark-python    # stop and remove the container
```

`--source` is the clone root: the key's paths (`testcode/BenchmarkTestNNNNN.py`) are relative to it.
`127.0.0.1` is allowed by the default scope (rule R3); nothing is added to `FlowStopper/`. `make bench`
(`scripts/bench.sh`) still targets only the we45 app; use the commands above for this one. No login
is needed, so there is no DAST auth config.

Regenerate the key (deterministic; aborts on any mismatch with the source):

```bash
.venv/bin/python bench/owasp-benchmark-python/build_key.py
make validate-key KEY=bench/owasp-benchmark-python/answer_key.json
```

## Keyed vulnerabilities

Every **in-scope** row of the official CSV is keyed: all `true` rows as vulns, all `false` rows as
decoys. Nothing is keyed that the CSV does not list. Each entry's `notes` / `reason` cites its CSV
row and the source URL at the pinned commit.

| CSV category | CWE | Kind | Vulns | Decoys (official `false`) | Runtime `param` set |
|---|---|---|---|---|---|
| sqli | 89 | pair | 5 | 11 | 1 of 5 |
| xss | 79 | pair | 31 | 58 | 12 of 31 |
| cmdi | 78 | pair | 13 | 7 | 6 of 13 |
| pathtraver | 22 | pair | 65 | 103 | 25 of 65 |
| redirect | 601 | pair | 13 | 21 | 3 of 13 |
| securecookie | 614 | runtime_only | 24 | 15 | n/a |
| **Total** | | | **151** (127 pair, 24 runtime_only, 0 code_only) | **215** | |

How each entry was built (`build_key.py`):
- **code** (pairs) = the test module `testcode/BenchmarkTestNNNNN.py`, lines = the whole nested
  `BenchmarkTestNNNNN_post` handler (each module holds exactly one test, so the handler span is
  unambiguous). The script checks the handler is on a POST `@app.route` naming the test and that the
  category's sink is inside it (`cur.execute`, `subprocess.run`/`os.system`, `open`/`codecs.open`/
  `exists`/`read_text`, `flask.redirect`, the returned HTML for XSS). The notes give the input line and
  sink line(s).
- **runtime** = the handler's route path, with `method` `null` (any method) when the module's GET
  handler on the same path is just `return BenchmarkTestNNNNN_post()` (140 of 151 vulns), and `POST`
  when the GET handler renders the form page instead (11 vulns). `param` is set only when the handler reads
  `request.form`/`request.args` by a literal name that the official crawler also sends as a form/query
  param; otherwise it is `null` (inputs from headers, cookies, the URL path, the raw query string,
  key loops or upstream's `request_wrapper` helper).
- **securecookie** = runtime-only (cookie flags are runtime-only in our scope). The script checks that
  the POST handler's `set_cookie(... secure=...)` flag agrees with the CSV verdict.
- **decoys** = the official `false` rows of the same six categories, at the `_post` handler span.

**Not keyed (outside our six types)**, all listed in the CSV: code injection (CWE-94, 20 vulnerable),
insecure deserialisation (502, 18), weak hashing (328, 71), LDAP injection (90, 16), trust boundary
violation (501, 18), weak randomness (330, 99), XPath injection (643, 51), XXE (611, 8).

**Also not keyed** (not in the official solution, so not ours to add): the literal `app.secret_key`
in `app.py`, debug mode, missing security headers, and the `Secure`-but-not-`HttpOnly` cookie that the
85 form-rendering GET handlers set.

## Caveats that affect measured metrics (not the key's correctness)

- **Nested routes.** Every test registers its two routes inside `def init(app):`, and `app.py` imports
  each module with `importlib` and calls `init(app)`. A route extractor that only reads module-level
  decorators will not see them.
- **Input sources.** Many vulnerable flows read headers, cookies, the URL path or the raw query string.
  A DAST that injects only query/form params will miss those; that is a true measurement.
- **GET usually reaches the flow too.** In 140 of the 151 keyed modules (and 1,145 of all 1,230), the
  GET handler just calls the POST handler, so the vulnerable code runs on either method; those keys
  leave `method` null. In the other 11 keyed modules GET only renders the form, so the key says `POST`.
  A handler that reads `request.form` still gets no input on GET; that is a property of the test.
- **Scale.** 1,230 test modules (2,460 routes plus the `/benchmark/<path:mypath>` page server).
- **Python 3.12** (upstream pins mitmproxy 11.1.3). Our Dockerfile installs only the packages the app
  imports (Flask, Werkzeug, Jinja2, MarkupSafe, itsdangerous, click, blinker, lxml, elementpath,
  PyYAML, ldap3, pyasn1) at upstream's pinned versions; the rest of `requirements.txt` is scanner
  tooling.
- **HTTP, not TLS.** Upstream runs `flask ... --debug --port 8443 --cert=adhoc`; we keep debug mode,
  drop the ad-hoc certificate and the reloader, and serve plain HTTP. The Werkzeug debugger is
  therefore live, so only publish on 127.0.0.1.
- **Writes files.** Some path-traversal tests open files for writing. Run it only in the container and
  use `make bench-down` (which removes the container) between runs so each scan starts fresh.
- **Non-root container.** Our Dockerfile runs the app as an unprivileged user that owns `/app`. Run as
  root, the write-mode traversal tests truncated `/etc/passwd` during a scan, which hid every later
  read-based traversal proof. This changes the measurement environment only, not the source (A-71).
